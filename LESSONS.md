# Lessons learned (Headroom)

- claude.ai's authorize page answers "Authorization failed / Invalid request format" for a short `state` (22-char base64) or `+`-encoded spaces. Send a UUID `state` and `%20`-encoded spaces (see `oauth::authorize_url`, `pkce::random_state`).
- `ksni` defaults to zbus's `tokio` feature. Cargo unifies it into the zbus that `keyring` uses, whose blocking Secret Service calls then `block_on` a tokio runtime inside ours: "Cannot start a runtime from within a runtime", then "LazyLock instance has previously been poisoned". Build ksni with `default-features = false, features = ["async-io"]` (`crates/headroom-app/Cargo.toml`), and check `cargo tree -i zbus -e features` when adding any zbus-based crate.
- GNOME Shell 46: horizontal `padding` on the `St.BoxLayout` inside an `St.ScrollView` is not repainted on scroll, so the strip next to the scrollbar keeps stale fragments of old rows. Put the padding on the `St.ScrollView` (`.headroom-scroll`), not on its child.
- The nested Shell (`dbus-run-session -- gnome-shell --nested`) has no Secret Service, so its app instance can't read any credential, and it shares `$HOME`: it writes "No default store has been set" backoffs into the real `~/.local/state/headroom/provider_state.json`. Test credentialed flows (claims, refresh) in the real session; use the nested Shell only for layout.
- An app started inside `dbus-run-session -- sh -c 'gnome-shell --nested --wayland & ... ./target/debug/headroom-app'` inherits the host's `WAYLAND_DISPLAY=wayland-0`, so its windows (panel, Settings) open on the real desktop while its D-Bus is the nested one: "clicking Settings does nothing". Start it with the nested socket: `WAYLAND_DISPLAY=wayland-1 ./target/debug/headroom-app` (check `ls /run/user/$UID/wayland-*`).
- QEMU test VM (`scripts/vm.sh`) with `-display gtk`: `virtio-vga` takes the guest size from the QEMU window (640x480 at boot), so `xres`/`yres`, `edid=off` and the kernel `video=` parameter don't fix the resolution. Use `-device VGA,edid=on,xres=…,yres=…`, which needs the `bochs` driver from `linux-image-extra-virtual` (the cloud image kernel lacks it). Check the real mode over SSH with `gdbus call ... org.gnome.Mutter.DisplayConfig.GetCurrentState` before asking the user to look.
- cloud-init `write_files` that creates `/etc/gdm3/custom.conf` before `gdm3` is installed makes dpkg stop at a conffile prompt, leaving gdm unconfigured (no `gdm` user, text login only). Install with `-o Dpkg::Options::=--force-confold`.
- The test VM's GNOME locks the screen after 5 idle minutes, and GNOME disables user extensions on the lock screen. A `headroom-app` started then sees no extension, tries the tray, finds no StatusNotifier host and exits. Keep the VM's lock off (`gsettings set org.gnome.desktop.session idle-delay 0`, `org.gnome.desktop.screensaver lock-enabled false`).
- SSH into the test VM fails with "Host key verification failed" (the key changes when the VM is recreated and is not in `known_hosts`). Use `ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o LogLevel=ERROR -i ~/.ssh/id_ed25519 -p 2222 dev@127.0.0.1`.
